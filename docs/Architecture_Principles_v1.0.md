# MakerStudio 아키텍처 원칙 — 점진적, 선택적 모듈화

**버전**: v1.0 · **작성일**: 2026-08-22
**짝 파일**: `MakerStudio_Project_Design_v2.6.md` §5.6 · `CLAUDE.md`

## 0. 이 문서의 목적

`Project_Design_v2.6.md` §5.5는 도메인별로 완전히 분리된 `/domains` + `packages/schema` +
이벤트 버스 구조를 목표 형태로 그려두었지만, 실제로는 이 구조를 한 번에 만든 적이 없다
(`app/api/{domain}/...` 폴더 관례로 도메인만 구분해왔고, 이벤트는 지금까지 전부 순수 함수
호출로 구현됨). 2026-08-22에 이 간극을 어떻게 좁혀갈지 **실행 순서**를 확정했고, 그 순서가
이 문서다 — §5.5의 이상향을 부정하는 게 아니라, 거기 도달하는 경로를 리스크 낮은 순서로
명시한 것이다.

## 1. 핵심 전략

**전체를 한 번에 완벽한 플러그형 아키텍처로 만들지 않는다.** 재사용 가치가 높고 위험이
낮은 부분부터 순서대로 인터페이스 뒤로 감춘다 — 큰 리팩터링을 한 번에 밀어붙이지 않고,
새 코드를 작성하는 시점마다 그 코드가 속한 영역부터 자연스럽게 전환한다.

## 2. 우선순위

| 우선순위 | 대상 | 전략 | 이유 |
|---|---|---|---|
| **1순위 — 즉시** | 결제(PortOne), SMS(Solapi), 이메일(Resend) | `PaymentProvider`/`SmsProvider`/`EmailProvider` 인터페이스로 추상화. 지금 구현체(`lib/billing/portone.ts`, `lib/sms/solapi.ts`, `lib/email/resend.ts`)는 그 인터페이스의 구현체 중 하나로 재배치 | 외부 벤더 종속성이 가장 높고, 각각 독립적인 I/O 경계라 위험 없이 지금 바로 감쌀 수 있다. 벤더 교체·다중 벤더 대응·테스트용 mock 구현체 필요성이 이미 존재(예: Solapi/Resend는 이미 "설정 안 되어 있으면 명확히 실패"라는 별도 정책이 있음 — 인터페이스화하면 이 정책도 한 곳에 모을 수 있다) |
| **2순위 — 점진적** | 각 도메인의 DB 접근 | Repository 계층으로 분리. 새 기능을 만들 때마다 해당 도메인부터 이 패턴으로 전환한다(보이스카웃 룰 — 손댈 때만 개선, 일괄 강제 리팩터링은 하지 않는다) | 도메인마다 시급성이 다르고, 지금 당장 전부 바꾸면 회귀 위험이 재사용 이득보다 크다. 새 기능 작업이 어차피 해당 도메인 코드를 건드리므로, 그 타이밍에 자연스럽게 전환 비용을 나눠 낸다 |
| **3순위 — 신중히, 나중에** | 인증(`ms_access_token` 패턴, `lib/client-auth.ts`) | `AuthAdapter` 인터페이스로 추출 — 단, **실제 두 번째 프로젝트가 생겨 요구사항이 확인된 후에만.** 지금은 건드리지 않는다 | 지금 모든 도메인이 이 패턴에 의존하는 핵심이라, 실사용처 없이 지금 인터페이스를 설계하면 잘못된 추상화를 굳힐 위험이 크다(YAGNI). 두 번째 실사용처가 생겨야 "무엇이 진짜 가변적인 부분인지"가 드러난다 |
| **대상 아님** | 한국 규제 로직(전자상거래법 다크패턴 금지 6유형, 개인정보보호법 만 14세 미만 동의, 정기결제 갱신 고지 등) | 항상 그대로 유지 — 인터페이스 뒤로 감추지 않는다 | 재사용을 노리는 관심사가 아니라 이 시장에서 지켜야 할 필수 제약이다. 다른 시장에 이식할 개념이 아니므로 추상화 대상 자체가 아니다 |

## 3. 실무 적용 가이드

- **새로 결제/SMS/이메일을 다루는 코드를 작성할 때**: 반드시 `PaymentProvider`/`SmsProvider`/
  `EmailProvider` 인터페이스 뒤로 감춘다(1순위, 즉시 적용 대상).
- **도메인 DB 접근 코드를 새로 작성하거나 손댈 때**: 가능하면 Repository 패턴으로 전환한다.
  기존 코드를 이 패턴으로 바꾸겠다고 별도 PR을 내지는 않는다 — 어차피 손대는 김에만 한다.
- **인증 패턴(`ms_access_token`, `authedFetch`, `getSupabaseServerClient()` 등)**: 지금은
  건드리지 않는다. `AuthAdapter`를 먼저 만들어두자는 제안이 나오면, "실제 두 번째 프로젝트
  요구사항이 확인됐는가"부터 되묻는다.
- **한국 규제 로직**: 인터페이스로 감싸거나 "나중에 다른 나라 규제로 교체 가능하게" 설계하지
  않는다. 이 로직은 재사용 가능한 관심사가 아니라 지금 이 시장의 필수 제약이다.
