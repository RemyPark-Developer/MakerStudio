## 0. 이 문서의 목적

`AI_PROJECT_RULES.md`는 "무엇을 만들 것인가(비전, UI 철학, 코딩 규칙)"를 정의합니다.
이 문서는 그보다 한 단계 앞선 질문 — **"세계적인 교육 플랫폼들은 왜 성공했고, 우리는 그중 무엇을 가져와야 하는가"** — 에 답하고,
그 답을 바탕으로 **로그인 / 결제 / 개발 방법론**까지 구체적인 설계로 연결합니다.

## 1. 벤치마크 분석 — 왜 이 플랫폼들인가

전 세계 메이커/코딩 교육에서 실제로 규모를 만든 6개 플랫폼을 선정해 분석했습니다. 기준은 "사용자 수", "완주율", "수익 모델의 지속가능성" 세 가지입니다.

| 플랫폼 | 핵심 강점 | MakerStudio가 가져올 것 |
|---|---|---|
| **Scratch** (MIT, 1억 명↑) | 코드 없이도 즉시 결과를 보는 블록 코딩. 실패해도 위험이 없는 "안전한 놀이터" | 초등 저학년 대상 **Blockly 브릿지 모드** — 텍스트 코드 이전 단계로 블록 코딩 옵션 제공 |
| **Tinkercad Circuits/Codeblocks** (Autodesk, 교육자 1억 명↑) | 하드웨어 없이 브라우저에서 회로를 "정말로" 시뮬레이션. 블록→텍스트 코드 자동 변환으로 학습 곡선을 완만하게 만듦 | 지금 데모의 SVG 회로도는 정적입니다. **실제 시뮬레이션 엔진**(§4 참고)으로 교체해야 진짜 경쟁력이 생김 |
| **Wokwi** (오픈소스, 대학 다수 채택) | 실제 AVR/ESP32 코드를 브라우저에서 그대로 컴파일·실행. VS Code/CI 연동까지 지원하는 "진짜" 임베디드 시뮬레이터 | MakerStudio의 "가상 컴파일" 연출을 **Wokwi 임베드 or 자체 AVR8js 엔진**으로 실제 실행 가능하게 전환 |
| **Duolingo** (5억 가입, DAU 5,650만) | 스트릭·XP·연속 학습으로 "그만두는 비용"을 심리적으로 크게 만듦. 무료 90% + 유료 전환 8.8%가 지속 가능한 프리미엄 구조 | 진행 단계 트래커를 **스트릭 + 배지 + 레벨 시스템**으로 확장 |
| **Khan Academy** (무료, 마스터리 러닝) | 다음 단원으로 못 넘어가는 게 아니라, "이해할 때까지" 반복하고 AI가 막힌 지점을 짚어주는 방식 | 지금의 "다음 단계 완료 ✓" 버튼을 **이해도 체크 기반 진급**으로 바꿔야 함 (퀴즈 통과해야 다음 실습 열림 등) |
| **Code.org** (전 세계 교육기관 도입, 교사 대상 무료) | 교사용 대시보드, 커리큘럼 표준 정렬, 학급 단위 진도 관리가 강력함 — **B2B(학교) 채널**이 매출의 실질적 축 | 로그인 설계에 "학생 개인" 외에 "교사 계정 → 학급 코드로 학생 초대" 구조가 반드시 필요 |

**결론 — 지금 데모에 없는데 반드시 있어야 하는 4가지**
1. 회로도가 "그림"이 아니라 **실제로 동작하는 시뮬레이터**여야 한다 (Tinkercad, Wokwi의 핵심)
2. 진급은 "버튼 클릭"이 아니라 **이해도 확인 후 진급**이어야 한다 (Khan Academy)
3. 개인 학습자 축과 별개로 **교사/기관용 학급 관리 축**이 있어야 한다 (Code.org)
4. 리텐션은 콘텐츠 양이 아니라 **스트릭/진행 시각화 같은 습관 설계**에서 나온다 (Duolingo)

## 2. 정보구조 (IA) — 두 개의 사용자 축

```
                         MakerStudio
                    ┌─────────┴─────────┐
              개인 학습자 축              기관/교사 축
        (초중고생, 대학생, 일반인)      (학교, 학원, 교사)
                    │                         │
        회원가입 → 보드 선택 → 예제         교사 가입 → 학급 생성
        → 9단계 학습 흐름 → 배지/스트릭     → 학급 코드 발급
                    │                         │
                    └──── 학생은 학급코드로 가입 (교사 축 종속) ──┘
```

개인 학습자와 기관 학습자를 **같은 학생 계정 모델** 위에 얹되, 기관 학습자는 `classroom_id`로 묶이고 진도가 교사 대시보드에 노출되는 구조를 권장합니다. Code.org, Khan Academy 모두 이 구조입니다.

## 3. 로그인 / 회원 설계

### 3.1 인증 방식
| 방식 | 대상 | 비고 |
|---|---|---|
| 소셜 로그인 (카카오, 네이버, Google) | 일반인, 대학생, 교사 | 국내 사용자 전환율을 위해 카카오 필수, 이메일 가입은 보조 수단으로만 |
| 학급 코드 가입 (비밀번호 없음) | 초·중학생 | 교사가 발급한 6자리 코드 + 닉네임만으로 로그인. 이메일/전화번호 없이도 가능하게 설계 |
| 교사/기관 계정 | 교사, 교육기관 담당자 | 이메일 + 소속기관 인증(선택) |

### 3.2 ⚠️ 반드시 지켜야 할 법적 요건 — 만 14세 미만 아동
대상 사용자에 **초등학생**이 명시되어 있으므로, 한국 개인정보보호법 제22조의2(아동의 개인정보 보호)가 그대로 적용됩니다.

- **만 14세 미만 회원가입 시 법정대리인(보호자) 동의가 법적으로 필수**입니다. 위반 시 과징금·과태료 대상입니다.
- 실무적으로 가장 흔히 쓰이는 방법은: 가입 시 보호자 휴대폰 번호를 받아 **문자 인증**으로 동의를 확인하는 방식입니다.
- 동의 확인을 위해 필요한 최소 정보(법정대리인 이름, 연락처)는 **동의 없이도** 아동으로부터 직접 수집이 가능합니다 (동의를 받기 위한 목적에 한함).
- **교사가 학급 코드로 초등학생을 일괄 초대하는 구조**를 쓰면, 학교가 이미 확보한 보호자 동의(가정통신문 등)를 활용할 수 있어 개인정보 수집 항목을 최소화(닉네임만)하는 것이 현실적인 해법입니다. 이 경우 이메일·전화번호를 아예 받지 않는 걸 권장합니다.
- 이 부분은 실제 서비스 오픈 전 **개인정보처리방침을 법률 검토** 받으시길 권합니다 — 저는 변호사가 아니며 이 문서는 참고용입니다.

### 3.3 권장 가입 플로우
```
[일반/대학생/성인]  소셜로그인 → 즉시 이용
[중·고등학생]        소셜로그인 또는 학급코드 → 즉시 이용 (만 14세 이상 가정)
[초등학생]           학급코드(교사 발급) + 닉네임만 → 보호자 동의는
                     교사가 사전에 오프라인/가정통신문으로 확보한 것을 전제
                     (개인 가입 시엔 보호자 휴대폰 인증 단계 삽입)
```

### 3.4 학급코드 공유 — 직접 메시징은 만들지 않는다

교사가 학급코드를 학생/학부모에게 전달하는 방법에 대해 **직접 문자·카카오톡 발송 기능은 만들지 않기로 결정**했습니다.

- 학교는 이미 카카오톡 학부모방·네이버 밴드·알림장 앱 등 자체 소통 채널을 갖고 있어, 이를 대체할 발송 인프라를 새로 만드는 것은 카카오 비즈니스 API 심사·문자 발송 비용·스팸 규제 준수 부담만 크고 차별화 효과가 없습니다. Google Classroom, Kahoot 등 비교 대상 서비스들도 자체 메시징 기능 없이 "복사해서 붙여넣기" 방식을 씁니다.
- 대신 **"옮기기 쉽게 만드는" 두 가지만 제공**합니다.
  1. **초대 링크**: 코드를 직접 부르는 대신 `makerstudio.example.com/join/{코드}` 형태의 링크 하나로 제공 — 교사가 기존 채널에 링크 하나만 붙여넣으면 됩니다.
  2. **인쇄용 가정통신문 PDF**: 학급코드 + QR코드 + 간단 안내문을 담은 PDF — 초등학생이 집에 들고 갈 종이 한 장이 필요하다는 점에서 Code.org 등이 이미 쓰는 방식입니다. §7.5에서 구축한 PDF 브랜딩 인프라(워크북/수료증)를 그대로 재사용해 추가 비용이 거의 들지 않습니다.

## 4. 결제 / 수익 모델

### 4.1 벤치마크 정리
Duolingo형 구조(무료 90% + 유료 10% 미만이 매출 대부분)는 **B2C 대규모 트래픽**이 있을 때만 성립합니다. MakerStudio는 초기에 그 트래픽이 없으므로, **B2C 프리미엄보다 B2B(학교/학원) 라이선스가 초기 현금흐름에 더 현실적**입니다.

### 4.2 ⚠️ 검토했다가 기각한 방식 — 포인트 충전형 모델
파일 다운로드 사이트류에서 흔한 "포인트 구매 → 콘텐츠별 포인트 차감 → 소진 시 충전 페이지 유도" 방식을 검토했으나 **채택하지 않기로 했습니다.**

- 이 방식은 정가를 부풀린 뒤 취소선으로 "할인"을 연출하거나(순차공개 가격책정), 무료/저가 체험 후 자동으로 정가 정기결제로 넘어가거나(숨은 갱신), 소진 시 결제 페이지로 반복 유도(반복 간섭)하는 패턴을 동반하는 경우가 많습니다.
- 한국은 **2025년 2월 14일 개정 전자상거래법**으로 이런 유형의 다크패턴 6가지(숨은 갱신·순차공개 가격책정·특정 옵션 사전선택·잘못된 계층구조·취소·탈퇴 방해·반복 간섭)를 명시적으로 금지했고, 2025년 10월 24일부터 시행 지침이 구체화되어 실제 집행되고 있습니다. 위반 시 시정조치·과태료(최대 500만원)·반복 위반 시 최대 1년 영업정지까지 가능합니다.
- MakerStudio는 초등학생~학부모가 결제를 판단하는 서비스이므로, 이런 구조는 법적 리스크는 물론 "차분하고 신뢰가는 학습 공간"이라는 브랜드 이미지와도 정면으로 배치됩니다. **화폐를 숨기지 않고, 항상 원화(₩)로 정직하게 보여주는 것 자체가 신뢰를 만드는 장치**라고 판단했습니다.

### 4.3 권장 모델 — 5-트랙 투명 가격제 (Family 트랙 추가)

| 트랙 | 대상 | 가격 구조 | 제공 범위 |
|---|---|---|---|
| **Free** | 모든 사용자 | 무료 | Blink 등 보드당 1~2개 입문 예제, AI 튜터 1일 질문 제한(예: 10회) |
| **Premium (개인 정기구독)** | 자녀 1명 또는 성인 개인 | 월 구독 고정가 1개만 (예: 월 9,900원), 원화로 명확히 표시 | 전 예제 잠금 해제, AI 튜터 무제한, 진도/배지 저장, 오프라인 PDF 워크북 |
| **Premium 가족 (신규)** | 보호자 1명 + 자녀 2~4명 | 월 정액 캡 1개만 (예: 월 19,900원, 최대 4명) — 인원수별 계단 요금 아님 | 등록된 모든 자녀 계정에 Premium 혜택 동일 적용, 자녀별 진도·배지는 완전히 분리 |
| **낱개 코스 구매 (선택)** | 구독 대신 필요한 것만 사고 싶은 사용자 | 코스별 고정가 (예: "Servo 모터 심화 코스 — 4,900원") — 포인트 환산 없이 원화 그대로 | 해당 코스 영구 이용권 |
| **Classroom (B2B)** | 학교/학원/교사, 자녀 5명 이상인 보호자 | 학급 단위 연간 라이선스 (좌석 수 기반, 예: "30석 — 연 300,000원") | 교사 대시보드, 학생 진도 일괄 관리, 커리큘럼 매핑 리포트, 세금계산서 발행 |

**Family 트랙 설계 원칙**
- **인원수별 계단식 요금(3명/5명/10명 이상 등)을 채택하지 않았습니다.** §8.1("화면당 하나의 결정") 원칙과 충돌하기 때문입니다 — 선택지가 많아질수록 보호자가 "어느 걸 사야 하지" 고민하다 이탈합니다. Spotify Family, Apple One Family처럼 **"최대 N명까지 한 가격"** 캡을 하나만 두는 방식을 채택했습니다.
- **5명 이상은 새 티어를 만들지 않고 기존 Classroom(B2B) 라이선스로 유도**합니다. 보호자 한 명이 자녀 5명 이상을 등록하는 상황은 사실상 소규모 공부방/기관에 가까워, 이미 있는 §4.3 학급 라이선스(10/30/50/100석)가 같은 문제를 이미 풀고 있습니다. 같은 문제를 두 번 풀지 않습니다.
- 자녀별 계정·진도는 Family 트랙에서도 완전히 분리되며, 결제만 보호자 1명에게 통합됩니다.

- **결제 없이 콘텐츠 자체는 계속 무료로 열어두는 것을 강력히 권장**합니다 — Duolingo, Khan Academy 모두 "무료로도 진짜 배울 수 있다"는 신뢰가 유료 전환의 전제 조건이었습니다.
- AI 튜터(API 호출 비용 발생)를 **무료/유료를 가르는 핵심 지표**로 쓰는 것이 합리적입니다. 무료는 일일 질문 수를 명확한 숫자로 제한하고, 유료는 구독 안에 "무제한"을 포함합니다 — 질문할 때마다 잔액을 걱정하게 만드는 종량제(질문당 과금)는 학습 경험 자체를 해치므로 지양합니다.
- **자동갱신 구독은 법적으로 갱신·가격 인상 30일 전 별도 명시적 동의 고지가 필수**입니다(개정 전자상거래법 제13조 제6항). 해지 절차도 가입만큼 쉬워야 하며("해지 방해"는 금지 대상), 오히려 "언제든 해지 가능, 해지해도 남은 기간은 그대로 이용" 문구를 결제 화면에 명확히 노출하는 것이 장기 재구독률에도 유리합니다.
- 피해야 할 것: 실제 판매된 적 없는 "정가"를 만들어 취소선 긋기, 사전 동의 없는 무료→유료 자동 전환, 소진 시 결제 페이지로 강제 이동, 긴급성을 강조하는 카피나 반짝이는 프로모션 배너.

### 4.4 결제 연동 (한국 기준)
- **PG사**: 포트원(구 아임포트) 또는 토스페이먼츠 — 두 곳 모두 국내 SaaS/에듀테크 스타트업이 가장 많이 쓰는 표준 연동이며, 카드/카카오페이/네이버페이를 한 번에 붙일 수 있습니다.
- **B2B 라이선스**는 카드 결제 외에 **세금계산서 발행 + 계좌이체(견적서 기반)** 플로우가 실제로 더 많이 쓰입니다. 학교/학원은 카드보다 이 방식을 선호합니다.
- 미성년자 본인 결제는 원칙적으로 지양하고, **보호자/기관 결제만 허용**하는 것을 권장합니다.

### 4.5 ⚠️ 계정 삭제 시에도 환불 거부는 불가 — 법적 검토 필요 (참고용, 변호사 검토 권장)

보호자가 **구독 기간이 남은 상태에서 계정(데이터) 삭제를 요청**하는 경우를 별도로 검토했습니다.

- **방문판매 등에 관한 법률 제31·32조(계속거래업자의 의무)**: 계속거래(구독) 계약을 맺은 소비자는 계약기간 중 언제든지 해지할 수 있고, 사업자는 대금 환급을 부당하게 거부해서는 안 됩니다.
- **약관규제법 제8·9조**: 고객에게 부당하게 불리한 해지 조항, 실제 손해를 초과하는 위약금 조항은 **무효**입니다.
- 공정위 가이드라인상 정상적인 환불은 **이용일수·회차에 비례하는 금액을 제외하고 환급**하는 것이 원칙이며, 이를 지키지 않는 것은 실제 다크패턴 단속 사례로 지적된 바 있습니다.

**계정 삭제가 상황을 복잡하게 만드는 지점**: 일반 구독 해지는 "결제 주기 종료일까지 계속 이용, 이후 환불 없음"으로 처리해도 문제가 없습니다(소비자가 지불한 만큼 서비스를 받으므로). 하지만 **계정 삭제는 데이터를 즉시 지우기 때문에, 남은 기간 동안 서비스를 받을 방법 자체가 사라집니다.** "서비스도 못 받고 환불도 못 받는" 상태가 되면 위 법 조항 위반 소지가 커지고, 삭제 요청(개인정보 권리 행사)을 이유로 금전적 불이익을 준 것으로 보일 경우 개인정보보호법상 문제도 겹칠 수 있습니다.

**설계 원칙**: **데이터 삭제(법이 요구하는 대로 지체없이 처리)와 구독 잔여기간 환불(일할 계산, 삭제 요청과 무관하게 처리)을 서로 독립적인 프로세스로 분리**합니다. 계정 삭제 확인 화면에도 이 두 가지가 별개로 처리된다는 것을 명확히 안내합니다.

> 참고: ChatGPT·Claude 같은 해외 서비스는 실제로 계정 삭제 시 잔여기간 환불을 명시적으로 보장하지 않습니다(원칙적으로 비환불, 사례별 예외만 검토). 하지만 이는 미국 등을 준거법으로 하는 해외 플랫폼이라 한국 소비자보호법 집행이 실무적으로 어렵기 때문에 가능한 관행에 가깝고, "법적으로 완전히 문제없다"는 의미는 아닙니다. VISION FOLLOWER는 한국 법인이 한국의 아동 이용자를 상대하는 서비스라 이런 해외 관행을 그대로 따르는 것이 오히려 더 위험합니다 — 국내 사업자는 소비자원·개인정보위의 집행 대상이 되기 훨씬 쉽기 때문입니다.

## 4-A. 부품 키트 판매 — 기존 쇼핑몰과의 관계

교육 콘텐츠(로그인 계정: 학생/교사, 아동 포함)와 실물 부품 커머스(결제: 성인/보호자, 배송·환불·CS 필요)는 **요구되는 개인정보 수준과 결제 주체가 근본적으로 다릅니다.** 그래서 완전 통합보다는 **"느슨한 연동(Loosely Coupled)"** 을 권장합니다.

### 검토한 3가지 방식

| 방식 | 내용 | 평가 |
|---|---|---|
| **A. 완전 통합** (계정·장바구니·결제 하나로) | MakerStudio 회원가입이 곧 쇼핑몰 회원가입, 하나의 장바구니/주문 시스템 사용 | 원스톱 경험은 좋지만, 학생(아동) 계정과 성인 결제·배송 정보가 한 시스템에 뒤섞여 개인정보처리방침이 복잡해지고, 학생 로그인 상태에서 결제 화면까지 자연스럽게 이어져 "미성년자 본인 결제 지양" 원칙과 충돌할 위험이 큽니다. 초기 개발 비용도 가장 큽니다 |
| **B. 단순 링크아웃** | "부품 구매하기" 버튼이 쇼핑몰 홈페이지나 검색결과로 단순 연결 | 구현은 가장 쉽지만, 사용자가 필요한 부품을 다시 검색·재구성해야 해서 이탈률이 높고 UX가 끊깁니다 |
| **C. API/딥링크 연동 (권장)** | 예제별 부품 세트를 쇼핑몰에 "스타터팩 SKU"로 미리 등록해두고, MakerStudio의 "장바구니에 담기" 버튼이 쇼핑몰의 장바구니 API를 호출해 해당 SKU를 자동으로 담아 쇼핑몰 결제 페이지로 이동시킴 | 로그인·개인정보·결제는 완전히 분리된 채로, 부품 재입력 없이 매끄럽게 이어짐. 개발 비용도 A보다 훨씬 적음 |

### 권장 구조
```
MakerStudio (교육 계정)              기존 쇼핑몰 (커머스 계정)
─────────────────────              ─────────────────────
학생/교사 로그인 (학급코드 등)         회원/비회원 구매, 결제, 배송, CS
예제별 "필요 부품" 카드                ← 스타터팩 SKU로 매핑
"장바구니에 담기" 버튼  ──[딥링크/API]──→  장바구니에 자동 담김 → 결제는 쇼핑몰에서
```
- **Phase 5(결제 도입) 즈음**에 우선 딥링크 연동만 넣고, 트래픽이 커지면 SSO(하나의 계정으로 양쪽 로그인)를 **교사/보호자 계정에 한해서만** 선택적으로 검토하는 것을 권장합니다. 학생(아동) 계정은 SSO 대상에서 제외해 결제 화면에 아예 닿지 않도록 하는 것이 안전합니다.
- 이 방식은 나중에 마음이 바뀌어도 되돌리기 쉽습니다 — API 연동은 실패해도 그냥 단순 링크(B)로 폴백하면 되고, 완전 통합(A)처럼 데이터 구조를 되돌리는 작업이 필요 없습니다.

### 4-B. 딥링크 연동 기술 스펙 (초안)

실제 구현 시 쇼핑몰 쪽에 아래 API 한 개만 열어주면 연동이 시작됩니다. (쇼핑몰이 자체 개발 사이트라는 전제로, 카페24/고도몰 같은 외부 솔루션이면 제공되는 오픈API로 대체)

**1) 스타터팩 SKU 사전 등록**
예제 하나당 부품 세트를 쇼핑몰에 실제 판매 상품(SKU)으로 하나씩 만들어둡니다.
```
MS-KIT-BLINK   Blink 스타터팩 (UNO+LED+저항+브레드보드+점퍼)   9,900원
MS-KIT-FADE    Fade 스타터팩 (Blink와 동일 구성)              9,900원
```
Blink/Fade처럼 실물 구성이 같은 예제는 같은 SKU를 공유해도 됩니다 — 재고 관리가 단순해집니다.

**2) MakerStudio → 쇼핑몰 장바구니 담기 요청**
```
POST https://shop.example.com/api/cart/add
Content-Type: application/json

{
  "sku": "MS-KIT-BLINK",
  "qty": 1,
  "source": "makerstudio",
  "ref": "blink",
  "return_url": "https://makerstudio.example.com/examples/blink"
}
```
- `source`/`ref` 값으로 어떤 예제에서 유입됐는지 추적 → 나중에 "어떤 콘텐츠가 구매 전환이 잘 되는지" 데이터로 활용 가능
- `return_url`로 결제 완료/이탈 후 학습 화면으로 되돌아올 수 있게 함
- 응답으로 쇼핑몰의 장바구니 페이지 URL(또는 리다이렉트 토큰)을 받아 새 탭으로 이동

**3) 실패 시 폴백**
API 호출이 실패하거나 타임아웃되면, 그냥 쇼핑몰의 해당 상품 페이지로 단순 링크(§4-A의 방식 B)로 넘어가도록 처리합니다. 즉 **C안이 실패해도 자동으로 B안으로 떨어지는 구조**라 서비스 장애로 이어지지 않습니다.

**4) 보안**
- 서버-투-서버 API가 아니라 브라우저에서 직접 호출하는 구조이므로, 판매 위조를 막기 위해 `source` 값에 대한 간단한 서명(HMAC) 정도는 붙이는 걸 권장합니다. 결제 자체는 전적으로 쇼핑몰 시스템 안에서 이뤄지므로 MakerStudio는 카드번호 등 결제 정보를 절대 다루지 않습니다.

```
학습자                MakerStudio               쇼핑몰
  │  "부품 담기" 클릭      │                        │
  ├───────────────────────▶│                        │
  │                        │  POST /cart/add        │
  │                        ├───────────────────────▶│
  │                        │◀───────────────────────┤
  │                        │  장바구니 URL 응답        │
  │◀───────────────────────┤                        │
  │  새 탭으로 쇼핑몰 장바구니 이동 (결제는 쇼핑몰에서 진행)   │
  └────────────────────────────────────────────────▶│
```

## 5. 기술 아키텍처

### 5.1 왜 지금 데모(Single HTML)로는 부족한가
`AI_PROJECT_RULES.md`의 "설치 없이 실행 / Single HTML 우선" 원칙은 **각 예제 프로토타입**에는 맞지만, 로그인·결제·진도 저장·교사 대시보드가 들어가는 순간 정적 HTML 한 장으로는 불가능합니다. 아래는 그 원칙을 최대한 지키면서 필요한 기능을 얹는 절충안입니다.

### 5.2 권장 스택 — "안전하고, 검증됐고, 단종 위험이 낮은" 것 기준으로 선정

기준은 세 가지입니다: **(1) 이미 수년~수십 년간 검증된 성숙한 기술인가, (2) 벤더가 망하거나 서비스를 접어도 탈출구가 있는가(오픈소스/자체 호스팅 가능 여부), (3) 국내 개발자 풀이 커서 유지보수 인력을 구하기 쉬운가.**

| 레이어 | 선택 | 이유 (안전성/유지보수 관점) |
|---|---|---|
| 언어 | TypeScript | JS에 타입을 더한 것뿐이라 학습장벽이 낮고, 마이크로소프트가 주도 · 업계 표준. 나중에 다른 개발자가 코드를 이어받기 쉬움(타입이 문서 역할) |
| 프런트엔드 | React (Next.js) | React는 10년 이상 검증된 메타(구 페이스북) 오픈소스, 웹 프런트엔드 사실상 표준. Next.js는 그 위에서 가장 많이 쓰이는 프레임워크로 채용 공고·레퍼런스가 압도적으로 많아 유지보수 인력 구하기 쉬움 |
| 백엔드/DB | Supabase (PostgreSQL 기반) | PostgreSQL은 1996년부터 이어진 오픈소스 DB로 사실상 "단종"이라는 개념이 없는 기술입니다. Supabase는 이 위에 인증·API·실시간 기능을 얹은 서비스인데, **핵심이 오픈소스라 자체 호스팅(self-host)으로 언제든 이전 가능** — 회사가 망해도 데이터와 코드를 그대로 들고 나올 수 있는 구조라는 게 가장 큰 안전장치입니다 |
| 인증 | Supabase Auth + 카카오 커스텀 프로바이더 | 백엔드와 한 벤더로 묶어 관리 포인트를 줄임. 소셜로그인 + 학급코드 로그인 혼합 지원 가능 |
| 회로 시뮬레이션 | Wokwi 임베드(iframe) 우선 → 장기적으로 avr8js 기반 자체 엔진 | Wokwi는 상대적으로 작은 회사라 유일하게 "벤더 종속" 리스크가 있는 항목입니다. 그래서 예제 스키마(§6.2)에서 회로 정보를 Wokwi 전용 포맷이 아니라 우리 자체 포맷(pin/parts)으로 저장해두는 걸 원칙으로 삼았습니다 — 나중에 Wokwi를 오픈소스 avr8js(MIT 라이선스, 자체 호스팅 가능)로 교체해도 콘텐츠 데이터는 그대로 재사용됩니다 |
| AI 튜터/콘텐츠 생성 | Claude API (서버 프록시 경유) | Anthropic API는 표준 REST 인터페이스라 특정 SDK에 종속되지 않음. 브라우저 직접 호출은 테스트용에 한하고, 실서비스는 반드시 백엔드가 중계 |
| 결제 | 포트원(PortOne) SDK | 여러 PG사(토스페이먼츠, 나이스페이 등)를 한 번에 연동해주는 "PG 어그리게이터"라 특정 PG사가 서비스를 접어도 코드 변경 없이 다른 PG로 전환 가능 |
| 배포 | Vercel(프런트) + Supabase(백엔드/DB 관리형) | Next.js를 만든 회사가 직접 운영하는 배포 플랫폼이라 호환성 문제가 생길 여지가 가장 적음. 두 서비스 모두 2026년 기준 스타트업 스택의 사실상 표준으로 자리잡아 있어 레퍼런스·문서·커뮤니티가 풍부합니다 |

**한눈에 보면**: 이 스택 전체에서 "회사가 망하면 정말 곤란해지는" 항목은 사실상 없습니다. DB(PostgreSQL), 프런트엔드 프레임워크(React) 핵심은 오픈소스고, 나머지(Supabase, Vercel, 포트원)는 전부 관리형 서비스가 죽어도 오픈소스 대안이나 경쟁 서비스로 갈아탈 수 있는 것들로만 골랐습니다. 유일하게 신경 쓸 부분은 Wokwi인데, 이것도 위에서 설명한 것처럼 데이터 포맷을 자체 소유로 유지해서 대비해뒀습니다.

### 5.3 마이그레이션 전략
바로 전체를 갈아엎지 말고 **단계적 전환**을 권장합니다.

1. **지금 만든 Single HTML 데모는 "예제 콘텐츠 템플릿"으로 유지** — 디자인 토큰, 카드 구조, 코드/퀴즈 UI는 그대로 재사용 가능
2. 그 위에 로그인/진도저장이 필요한 부분만 **얇은 Next.js 셸**로 감싸기 (예제 화면 자체는 지금 구조를 컴포넌트화)
3. 회로 시뮬레이션만 먼저 Wokwi로 교체 (가장 티가 나는 "가짜" 부분)
4. AI 튜터를 서버 프록시로 이전 (보안/과금 제어)
5. 교사 대시보드, 결제는 가장 마지막 — **콘텐츠 5~10개가 확보된 뒤** 붙이는 게 낭비가 적음

### 5.4 형상관리 — Git + GitHub

네, **Git과 GitHub를 기본으로 사용하는 걸 전제로 설계**했습니다. 이유와 구체적인 활용 방식은 다음과 같습니다.

- **왜 필수인가**: Git은 2005년부터 이어진, 사실상 유일한 표준 형상관리 도구입니다(단종 리스크 자체가 없는 영역). GitHub는 Microsoft 소속으로 가장 안정적인 호스팅 서비스이고, 무엇보다 **§6.3의 AI 콘텐츠 검증 파이프라인을 GitHub Actions로 그대로 구현**할 수 있다는 실질적인 이유가 큽니다.
- **브랜치 전략(제안)**: `main`(운영 배포) / `dev`(통합 테스트) / `feature/*`, `content/*`(기능·콘텐츠별 작업 브랜치). AI가 생성한 콘텐츠 모듈도 `content/ultrasonic-sensor` 같은 브랜치 + PR로 들어오게 하면, 사람이 승인하기 전 자동 검증을 끼워넣기 자연스럽습니다.
- **GitHub Actions로 자동화할 것**:
  - 코드 PR: 빌드/타입체크/린트 자동 실행
  - **콘텐츠 PR(AI 생성 모듈)**: §6.3의 "2단계 자동 검증"을 여기서 실행 — JSON 스키마 유효성 검사 + arduino-cli 컴파일 테스트를 GitHub Actions 워크플로우로 돌려서, 통과해야만 사람 검수 단계로 넘어가도록 구성
  - `main` 브랜치에 머지되면 Vercel이 자동 배포(Vercel의 GitHub 연동 기본 기능)
- **저장소 구조(제안)**:
  ```
  /apps/web            → Next.js 프런트엔드
  /content/examples    → 개별 모듈 JSON (§6.2 스키마)
  /content/courses     → 코스 JSON (§6.5 스키마)
  /packages/schema     → JSON 스키마 정의 (콘텐츠 검증에 공용 사용)
  /.github/workflows   → CI (빌드, 콘텐츠 검증)
  ```
- 비공개 저장소(Private repo)로 시작해서, 나중에 예제 콘텐츠 일부를 오픈소스로 공개하는 것도 커뮤니티 기여를 받는 좋은 확장 경로가 될 수 있습니다 (Scratch, Wokwi 모두 이 방식으로 성장했습니다).

### 5.5 느슨한 결합 아키텍처 — 멀티 에이전트/분업 개발 대비

본격적인 개발 단계에서는 로그인, 결제, 콘텐츠 파이프라인, 학습 화면, 관리자 검수 등을 **서로 다른 담당(사람이든 AI Agent든)이 동시에 나눠 맡을 수 있어야** 합니다. 이를 위해 지금부터 "도메인 경계"를 명확히 그어두는 것을 권장합니다.

**원칙 — 도메인은 서로의 내부를 직접 건드리지 않는다**
각 도메인은 자신의 데이터와 로직을 스스로 소유하고, 다른 도메인과는 오직 **(1) 정의된 API** 또는 **(2) 이벤트(발행/구독)** 로만 통신합니다. 한 도메인 담당자(Agent)가 다른 도메인의 DB 테이블이나 내부 함수를 직접 참조하는 순간 결합이 강해지고, 나중에 그 도메인을 독립적으로 수정·배포·교체하기 어려워집니다.

**도메인 구분(제안)**

| 도메인 | 책임 | 예시 |
|---|---|---|
| `content` | 콘텐츠 스키마, AI 생성, 버전 관리, 생애주기 상태(§6.3) | 모듈/코스 JSON, 자동검증 |
| `moderation` | 관리자 검수, 승인/반려, 검수 이력 | 관리자 대시보드 백엔드 |
| `identity` | 로그인, 역할(학생/보호자/교사/관리자), 학급코드 | 인증, 권한 |
| `billing` | 구독, 낱개구매, 결제 웹훅 | 포트원 연동 |
| `learning` | 진도, 퀴즈, AI 튜터, 배지 | `/api/tutor`(이미 이 원칙으로 구현됨) |
| `commerce-integration` | 쇼핑몰 딥링크(§4-B) | 장바구니 연동 |
| `notifications` | 이메일/인앱 알림 (다른 도메인의 이벤트를 구독만 함) | "코스 출시됨", "요청 승인됨" |

**도메인 간 통신 — API 우선, 이벤트로 비동기 처리**
- 즉시 응답이 필요한 것(예: billing이 identity에게 "이 사용자 로그인 상태인가?" 확인)은 **API 호출**로.
- 한 도메인의 상태 변화가 다른 도메인에 파급되는 것(예: content가 "코스 승인됨" 상태가 되면 notifications가 알림 신청자에게 메일을 보내야 함)은 **이벤트**로 처리합니다. `content` 도메인은 `content.published` 이벤트만 발행하면 되고, 그걸 누가 구독해서 뭘 하는지는 몰라도 됩니다 — 나중에 `notifications` 담당(Agent)이 새로 투입돼도 `content` 쪽 코드를 한 줄도 안 건드리고 구독만 추가하면 됩니다.
- MVP 단계에서는 별도 메시지 큐 없이 **인메모리/DB 테이블 기반의 단순 이벤트 로그**로 시작하고, 트래픽이 커지면 Supabase의 webhook 기능이나 큐 서비스로 교체 가능하도록 인터페이스만 지금부터 고정해둡니다.

**공용 계약(Contract)은 하나로 통일**
모든 도메인이 같은 데이터 모양을 다르게 이해하면 결합이 오히려 강해집니다. `packages/schema`(이미 §5.4에서 계획한 폴더)를 **모든 도메인이 함께 참조하는 유일한 진실 공급원(single source of truth)** 으로 삼습니다 — 콘텐츠 스키마, 사용자 역할, 이벤트 타입 정의가 전부 여기 있고, 각 도메인은 이걸 import만 합니다.

**저장소 구조(개정)**
```
/apps/web                    → Next.js 프런트엔드 (각 도메인 API를 소비)
/domains
  /content                    → 콘텐츠 파이프라인 (§6)
  /moderation                 → 관리자 검수 (§6.3)
  /identity                   → 로그인/역할 (§3)
  /billing                    → 결제/구독 (§4)
  /learning                   → 진도/퀴즈/AI튜터 (이미 /api/tutor로 이 패턴 적용됨)
  /commerce-integration        → 쇼핑몰 딥링크 (§4-B)
  /notifications               → 알림 (다른 도메인 이벤트 구독)
/packages
  /schema                      → 공용 타입/스키마 (Zod) — 유일한 진실 공급원
  /events                      → 도메인 간 이벤트 타입 정의
```

**지금 당장 얻는 이점**: 도메인 폴더가 나뉘어 있으면, 앞으로 특정 영역(예: 결제)을 다른 AI Agent나 개발자에게 맡길 때 "이 폴더 안에서만 작업하고, 다른 도메인과는 `packages/schema`와 이벤트로만 소통하라"는 규칙 하나로 충돌 없이 병렬 작업이 가능해집니다.

## 6. AI 콘텐츠 자동 생성 파이프라인 (플러그인 구조)

### 6.1 왜 지금 구조가 이미 절반은 준비되어 있는가
지금 데모(Blink/Fade)는 내부적으로 하나의 JS 객체(`EXAMPLES`)에 제목/부품/회로 파라미터/코드/설명/퀴즈/미션이 스키마처럼 정리되어 있습니다. 이 구조를 외부 JSON 파일들로 분리하면, **"이 스키마에 맞는 JSON 파일 하나를 추가하는 것 = 예제 하나가 플러그인되는 것"** 이 됩니다. AI 자동 생성은 이 스키마에 맞는 JSON을 채우는 작업으로 정의할 수 있습니다.

### 6.2 콘텐츠 스키마 (개정 — 다국어 대비 + 버전 필드 추가)

지금은 모듈이 3개뿐이라 스키마를 바꾸는 비용이 가장 쌉니다. 나중에 "전세계적으로 독보적인 교육 포털"이 목표라면 다국어가 필수인데, 텍스트 필드를 한국어로 하드코딩해두면 모듈이 100개 넘어간 뒤에는 전부 다시 구조를 짜야 합니다. 그래서 지금부터 텍스트 필드를 언어별 객체로 바꿔둡니다.

```json
{
  "id": "ultrasonic",
  "icon": "📡",
  "label": { "ko": "초음파 센서", "en": "Ultrasonic Sensor" },
  "difficulty": 2,
  "estimatedMinutes": 30,
  "pin": "D9 (Trig) / D10 (Echo)",
  "intro": { "ko": "...", "en": "..." },
  "parts": ["Arduino UNO", "HC-SR04", "점퍼 와이어 x4"],
  "circuit": { "type": "digital-io", "pins": {"trig":9,"echo":10} },
  "code": "void setup(){ ... }",
  "explain": { "ko": "...", "en": "..." },
  "mission": { "ko": "...", "en": "..." },
  "quiz": { "question": {"ko":"...","en":"..."}, "options": [...], "answer": 1, "explain": {"ko":"...","en":"..."} },
  "sourceExample": "Arduino IDE 공식 예제 - Sensors (public domain)",

  "version": 1,
  "status": "published",
  "lastVerifiedAt": "2026-08-12T00:00:00Z"
}
```

- 초기에는 `ko`만 채우고 `en`은 비워둬도 스키마 자체는 이미 다국어 대응 형태라 나중에 번역만 채우면 됩니다 (구조 재설계 불필요).
- `code`, `pin`, `parts`처럼 언어 무관한 필드(코드, 부품명 고유명사)는 그대로 단일 문자열 유지.
- `version`, `status`, `lastVerifiedAt`은 §6.3의 생애주기 관리에 쓰입니다.

### 6.3 생성 파이프라인 — 콘텐츠 생애주기 (개정)

기존 "4단계 게이트"를 실제 운영에 필요한 상태 전이로 구체화했습니다. 반려에는 성격이 다른 두 종류가 있다는 걸 반영한 것이 핵심 변경점입니다.

```
DRAFT (AI 초안)
   → 자동검증 (JSON 스키마 + 실제 컴파일)
       ├─ 실패 → DRAFT 복귀, AI가 자동 재생성 (사람 개입 없음)
       │         └─ N회(예: 3회) 연속 실패 → AUTOMATION_STUCK ← §6.3-b 참고
       └─ 통과 → PENDING_REVIEW   ← 카탈로그에 "출시 예정"으로 노출 가능한 최초 시점
              ├─ 승인 → PUBLISHED (v1, 카탈로그에서 구매 가능)
              ├─ 반려-재작업 (품질 문제) → DRAFT 복귀, "출시 예정" 상태 유지, 예상 시기만 조정
              └─ 반려-철회 (사업적 판단: 부품 단종·우선순위 변경 등)
                     → WITHDRAWN (이력 보관, 출시 예정 알림 신청자에게 솔직히 통지)
                     → 관리자가 나중에 "재작업 지시" 가능 → DRAFT로 부활

PUBLISHED (v1, 판매 중)
   → 고객이 "이 모듈 개선 제안하기" 제출 (learning 도메인 → content 도메인으로 이벤트 전달)
       → REVISION_DRAFT 생성 (기존 v1은 그대로 판매·서비스 유지, 학습자 혼란 없음)
       → 자동검증 → PENDING_REVIEW → 승인 → v2로 교체
              (신규 학습자는 v2, 이미 학습 중이던 사용자는 §6.3-a 정책에 따름)
```

**핵심 규칙들**
- **"출시 예정" 배지는 오직 `PENDING_REVIEW` 상태에만 붙입니다.** 아직 AI가 생성조차 안 한 로드맵 항목을 마케팅 목적으로 "출시 예정"이라 부르지 않습니다 — §4.2에서 "실제 없던 걸 있는 것처럼 보여주지 않는다"는 원칙과 일관성을 맞춘 것입니다.
- **철회(WITHDRAWN)는 삭제가 아니라 이력 보관입니다.** 나중에 관리자가 재작업을 지시하면 DRAFT로 되살릴 수 있고, 왜 철회했는지 사유도 함께 남깁니다.
- **이미 판매 중인 콘텐츠도 버전(`version`)을 매깁니다.** 업데이트가 기존 학습자의 진행 중인 학습을 갑자기 바꿔버리지 않도록, 새 버전은 신규 학습자부터 적용하는 것을 기본으로 합니다 (App Store 업데이트 방식과 동일한 원리).
- **`lastVerifiedAt`을 카탈로그/코스 상세 화면에 정직하게 노출**합니다 — "이 코드 마지막 검증일" 같은 신뢰 지표는 대부분의 경쟁 서비스가 숨기는 정보라, 오히려 공개하는 것 자체가 차별화 요소가 됩니다 (§8 고객 경험 원칙 참고).

### 6.3-a "이미 학습 중이던 사용자" 버전 고정 정책 (2026-08-21 확정·구현)

§6.3 본문(384행)이 이 섹션을 인용만 하고 실제 정의가 없던 상태였다. 정책은 다음과 같다.

**정책 3줄 요약**
1. 콘텐츠가 v2로 업그레이드되어도, 이미 v1을 학습 중이던 사용자는 App Store 업데이트
   방식처럼 계속 v1을 본다 — 자동 전환 없음.
2. 신규 학습자(그 콘텐츠를 한 번도 접한 적 없는 사용자)만 v2를 본다.
3. **"학습 중"의 판정 기준**: 그 콘텐츠에 대해 `learning_progress` 행이 이미 존재하는
   사용자(퀴즈를 한 번이라도 제출한 적 있음). 처음 접하는 사용자만 최신 버전을 본다.

**실제 구현은 위 §6.3 다이어그램(REVISION_DRAFT, 고객 제출 이벤트)을 다음 세 가지로
단순화했다** — 이 저장소엔 이벤트 버스도, 비관리자 콘텐츠 제출 플로우도 없기 때문
(§5.5, `Session_2026-08-20_Summary` §4):

- **트리거는 고객 제출이 아니라 관리자가 직접 누르는 버튼**이다(`app/admin/content-review`의
  "개선판 만들기"). 게시된 콘텐츠를 복제해 다음 버전의 `pending_review` 행을 즉시 만든다 —
  이미 검증된 코드를 그대로 복제한 것이라 `DRAFT`의 자동 재검증 단계(스키마+컴파일)를
  건너뛴다. `status` enum에 별도 `REVISION_DRAFT` 값은 두지 않고, `version > 1`이 곧
  "이건 개선판"이라는 표식 역할을 한다 — 기존 검수 목록·승인/반려 API를 그대로 재사용하기
  위한 의도적 단순화.
- **`id`(PK)와 `slug`(버전 무관 식별자)를 분리**했다(`content_modules.slug`, 0032 마이그레이션).
  기존 행은 `slug = id`로 백필돼 URL·학습 진도가 그대로 유효하고, 개선판은 새 `id`
  (`{slug}-v{version}`)를 받지만 `slug`는 유지한다 — 같은 슬러그로 여러 버전이 동시에
  `published`일 수 있다. 카탈로그(`GET /api/content/examples`)는 항상 슬러그당 최신 버전만
  노출한다.
- **어느 버전을 보여줄지는 읽기 시점에 서버가 계산**한다(`lib/content/publishedModules.ts`의
  `getPublishedModuleForUser()`) — 사용자 진도(`learning_progress.started_at`)가 각 버전이
  `published`로 승인된 시점(`content_modules.updated_at`)보다 나중인, 가장 높은 버전에 고정한다.
  퀴즈 제출 경로(`/api/learning/quiz`, `submit_quiz_attempt` RPC)는 원래도 슬러그를
  `module_id`로 써왔으므로 **전혀 건드리지 않았다** — 새 컬럼·RPC 변경·프론트엔드 변경 없이
  기존 안정 경로를 그대로 재사용. **전제**: `content_modules`에 "승인 후 재수정" 기능이
  아직 없어서 `updated_at`이 "언제 published됐는가"를 항상 정확히 반영한다 — 나중에 게시된
  콘텐츠를 다시 편집하는 기능이 생기면 이 전제가 깨지니 그때 별도 `published_at` 컬럼으로
  전환할 것.

### 6.3-b ⚠️ 컴파일 실패는 원칙적으로 관리자가 보지 않는다

**흔한 오해를 정정합니다**: "컴파일 실패"는 기계가 이미 자동으로 판단을 끝낸 문제라, 정상적인 경우 `PENDING_REVIEW`(사람의 커리큘럼 판단 대상)에 절대 섞이지 않습니다. 관리자가 검수하는 건 "코드가 도는가"가 아니라 **"내용이 교육적으로 적절한가"** 처럼 기계가 판단할 수 없는 것들입니다.

유일한 예외는 **AI가 자동 재생성을 반복해도 계속 실패하는 경우**입니다. 이건 프롬프트나 소스 예제 자체에 구조적 문제가 있다는 신호이고, 무한 자동 재시도는 API 비용만 낭비합니다. 이 경우에만 `AUTOMATION_STUCK`이라는 **별도 상태·별도 화면 섹션**으로 관리자에게 넘어갑니다 — "이 콘텐츠 내용이 괜찮은가"(커리큘럼 판단)와 "시스템이 왜 자꾸 실패하는가"(기술적 디버깅)는 완전히 다른 종류의 검토라, 같은 목록에 섞으면 관리자가 혼란스러워합니다. 관리자 화면에도 이 둘은 시각적으로 분리된 섹션으로 보여줍니다.

### 6.4 장기적으로 고려할 것
- 회로도 SVG 자체도 partsList/pin 정보를 기반으로 자동 생성하는 것을 고려할 수 있습니다 (지금은 breadboard+LED 레이아웃이 고정이라 수동 조정이 필요한 컴포넌트도 있음 — 센서/모터류는 SVG 템플릿을 몇 개 더 준비해두고 매칭하는 방식 추천)
- AI가 생성한 콘텐츠 품질을 추적하기 위해, 검수 단계에서 반려된 항목과 사유를 로그로 남겨 프롬프트를 지속적으로 개선하는 루프를 두는 것을 권장합니다
- **수익성 KPI로 추적할 것 — "모듈 재사용률"**: §6.5의 "코스는 기존 모듈 재조합"이 사실 수익성의 핵심 레버입니다. 모듈이 쌓일수록 새 코스 제작의 한계비용이 0에 가까워지기 때문입니다. "신규 코스 중 몇 %가 기존 모듈 재사용으로 만들어졌는가"를 실제 지표로 추적하면, 콘텐츠 라이브러리가 커질수록 수익성이 구조적으로 개선되고 있다는 걸 숫자로 증명할 수 있습니다.

### 6.5 콘텐츠 소싱 전략 — 공식 예제 → 복합 키트 코스

**1단계: 보드별 공식 예제를 소스로 사용**
"막연한 주제"를 AI에게 던져서 코드를 새로 창작하게 하는 대신, 각 보드가 이미 제공하는 **공식 예제(Arduino IDE의 File → Examples, ESP32 Arduino Core 예제, micro:bit MakeCode 예제, Raspberry Pi Pico MicroPython 예제)를 코드 소스로 사용**합니다. 이 코드는 이미 컴파일·동작이 검증된 상태라, AI의 역할이 "코드를 새로 쓰는 것"에서 "이미 맞는 코드를 우리 스키마·설명 형식으로 재구성하는 것"으로 바뀌어 훨씬 안전합니다. 보드별로 Basics → Digital → Analog → Communication → Sensors 순으로 이미 난이도가 정렬돼 있는 것도 그대로 커리큘럼 순서로 활용할 수 있습니다.

> ⚠️ 라이선스 참고: 대부분의 Arduino 공식 예제는 코드 주석에 "public domain"으로 명시돼 있어 재사용에 문제가 없지만, 일부 서드파티 라이브러리 예제는 LGPL/MIT 등 다른 라이선스를 가질 수 있어 라이브러리별로 확인이 필요합니다. 또한 Arduino 공식 문서의 **설명 문장 자체를 그대로 복사하는 것은 피하고, 설명·퀴즈·미션은 항상 새로 작성**해야 합니다(저작권 + 우리 톤 유지 목적 모두 해당).

**2단계: 복합 키트(자동차/로봇 키트)를 위한 "코스" 레이어 추가**
자동차 키트, 로봇 키트는 예제 하나가 아니라 "모터 제어 + 초음파 장애물 회피 + 라인트레이싱 + 블루투스 조종"처럼 여러 개별 모듈이 순서대로 엮인 묶음입니다. 이를 위해 스키마에 `course` 타입을 추가합니다.

```json
{
  "id": "smartcar-kit-101",
  "type": "course",
  "label": "4WD 스마트카 키트 입문",
  "kitSku": "MS-KIT-SMARTCAR",
  "modules": ["motor-basic", "ultrasonic", "line-tracking", "bluetooth-control", "smartcar-final-project"],
  "finalProject": "smartcar-final-project"
}
```
개별 모듈(`motor-basic`, `ultrasonic` 등)은 6.2의 예제 스키마를 그대로 쓰고, `course`는 이 모듈들을 순서대로 묶는 "목차" 역할만 합니다. 이렇게 하면 같은 모듈(예: "라인트레이싱")을 다른 로봇 키트의 코스에도 재사용할 수 있어, 키트 종류가 늘어나도 모듈을 처음부터 다시 만들 필요가 없습니다. `kitSku`는 §4-B의 딥링크 연동에서 그대로 사용되어, 코스 페이지의 "이 키트 담기" 버튼과 자연스럽게 연결됩니다.

**3단계 이후: 이 방식의 반복**
1~2단계가 안정화된 뒤에는 새로운 보드나 새로운 키트가 추가될 때마다 같은 절차(공식 예제 소싱 → 모듈화 → 필요 시 코스로 묶기)를 반복하는 것만으로 콘텐츠 라이브러리가 확장되는 구조입니다.

### 6.6 카탈로그 노출 원칙 — "출시 예정"은 근거가 있어야 한다

카탈로그 화면에 아직 완성되지 않은 코스를 보여줄 때는 두 가지를 지킵니다.

1. **"지금 배울 수 있어요"와 "출시 예정"을 화면에서부터 명확히 분리**합니다 — 같은 카드 디자인에 다른 문구만 넣지 않고, 아이콘 채도·배지·버튼 문구(구매 가능은 "코스 목차 보기", 준비중은 "🔔 출시 알림 받기")까지 다르게 해서 클릭 전에 오해가 없도록 합니다.
2. **"출시 예정" 배지는 §6.3의 `PENDING_REVIEW` 상태에만 붙입니다.** 아직 자동검증조차 통과하지 못한(=AI가 초안조차 못 만든) 로드맵상의 아이디어를 "출시 예정"이라고 부르지 않습니다. 이는 §4.2에서 지켜온 "실제 없는 것을 있는 것처럼 보여주지 않는다"는 원칙의 연장입니다.
3. **철회(WITHDRAWN)되면 카탈로그에서 조용히 사라지게 두지 않고, "출시 예정" 알림을 신청했던 사용자에게 개별 통지**합니다. 아무 말 없이 사라지는 건 "약속했다가 몰래 발뺌"하는 다크패턴과 정신적으로 같은 문제이기 때문입니다.

### 6.7 관련 코스 추천 — 두 가지 방식을 절대 섞지 않는다

코스 상세 화면의 "관련 코스" 섹션은 근거가 서로 다른 두 방식으로 나뉘고, **문구도 그 근거에 맞게 정직해야 합니다.**

| 방식 | 근거 | 적용 가능 대상 | 문구 예시 |
|---|---|---|---|
| **행동 기반** | 실제 사용자의 공동구매·공동이수 데이터 | `PUBLISHED` 상태 코스만 (실제 구매·이수 기록이 있는 것만) | "함께 학습한 학습자가 다음으로 선택한 코스" |
| **콘텐츠 기반** | 보드 종류·겹치는 개념 태그 등 콘텐츠 유사도 (사용자 행동과 무관) | `PENDING_REVIEW`("출시 예정")도 포함 가능 | "비슷한 개념을 다루는 다른 코스" |

**절대 규칙**: 실사용자 행동 데이터가 없는 상태(Phase 3 이전, 또는 서비스 초기 트래픽이 적을 때)에서는 **"많이 본", "인기 있는" 같은 행동 기반 문구를 절대 쓰지 않습니다.** 데이터가 없는데 있는 것처럼 표현하는 것은 §4.2·§6.6에서 지켜온 "실제 없는 것을 있는 것처럼 보여주지 않는다" 원칙을 그대로 위반하는 것입니다. 콘텐츠 기반 추천에 `PENDING_REVIEW`(출시 예정) 코스를 섞는 것은 괜찮지만, 그 경우도 "인기"가 아니라 "관련 있음"으로만 설명합니다.

Phase 3 이후 실제 이용 데이터가 쌓이면, 행동 기반 추천을 콘텐츠 기반과 나란히(또는 대체) 배치할 수 있습니다 — 단, 그 시점에도 §6.7의 표를 기준으로 두 방식의 데이터 출처를 섞지 않습니다.

## 7. 콘텐츠 보호 원칙 (상설 — 새 기능 설계 때마다 항상 재확인)

콘텐츠(코드, 설명, 워크북 등)를 경쟁사나 악의적 사용자가 무단으로 가져가는 것을 막기 위한 원칙입니다. 새로운 화면·기능을 설계할 때마다 이 섹션을 다시 점검합니다.

### 7.1 기본 전제
**"완전 차단"은 불가능합니다.** 로그인한 사용자가 화면으로 보는 이상 화면 캡처·타이핑으로 베끼는 것 자체는 막을 수 없습니다(모든 콘텐츠 플랫폼 공통 한계). 그래서 목표는 세 가지로 잡습니다: **(1) 대량으로 쉽게 못 긁어가게, (2) 유출돼도 추적 가능하게, (3) 애초에 통째로 베낄 가치를 낮추게.**

### 7.2 ⚠️ 반드시 지켜야 할 구조 원칙 — 서버 권한 확인 없이 잠긴 콘텐츠를 빌드하지 않는다
Next.js의 정적 생성(SSG)은 빌드 시점에 모든 데이터를 결과물에 포함시킵니다. **Premium으로 잠긴 모듈이라도 SSG로 빌드하면, UI만 잠긴 척할 뿐 실제 코드/설명은 이미 응답(페이지 소스, API 응답)에 그대로 노출됩니다.** 이는 발견 즉시 원칙으로 못 박은 사항입니다.

- 무료(Free) 콘텐츠: SSG 그대로 사용 가능 (지금 Blink/Fade/초음파 센서가 이 경우)
- 잠긴(Premium/낱개구매) 콘텐츠: **반드시 서버가 로그인·구독·구매 상태를 확인한 뒤에만 응답에 포함**시켜야 합니다 (서버 렌더링 또는 API 게이팅 필수). 로드맵상 Phase 3(로그인) 이후 첫 유료 모듈을 추가할 때 이 원칙을 지키는지 반드시 확인합니다.

### 7.3 계층별 방어

| 계층 | 조치 |
|---|---|
| 서버 권한 확인 | §7.2 원칙 — 가장 근본적인 방어 |
| 이상 사용 탐지 | 짧은 시간에 대량 API 호출(스크래핑 패턴) 하는 계정 탐지 후 정지 |
| 워터마크 | PDF 워크북에 구매자 식별정보를 삽입해 유출 경로 추적 가능하게 — §7.5에서 구체 사양 정리 |
| 학급코드 남용 탐지 | 라이선스 좌석 수보다 훨씬 많은 기기에서 로그인되면 알림 |
| 법적 장치 | 이용약관에 재배포 금지 명시 + 저작권 신고·삭제 절차 준비 |

### 7.4 전략적 관점 — 코드 자체보다 "베껴도 못 따라오는 것"에 집중
§6.5에서 콘텐츠를 공식 예제(대부분 public domain) 기반으로 소싱하기로 했기 때문에, **코드 자체는 원래 어디서나 구할 수 있는 것**이라 지켜봤자 방어 효과가 작습니다. 실제로 지킬 가치가 있고 통째로 복제하기 어려운 자산은 **커리큘럼 순서 설계, AI 튜터와의 상호작용, 실물 키트와 묶은 학습 경험, 진도/배지 시스템** 같은 것들입니다. 콘텐츠 보호에 과도한 리소스를 쓰기보다, 이 부분을 계속 잘 만드는 데 무게를 두는 것이 전략적으로 더 유효합니다.

### 7.5 PDF 워크북 브랜딩·워터마크 사양

Premium 혜택으로 약속된 PDF 워크북에는 다음 요소를 반드시 포함합니다 (샘플 PDF로 실제 검증 완료).

| 요소 | 내용 | 목적 |

| 상단 브랜드 바 | MakerStudio 로고 + "제작: VISION FOLLOWER"(회사명) | 브랜드 신원 명시 |
| 대각선 워터마크 | "{구매자 닉네임} 님 전용 · {주문번호}"를 반투명하게 전체 페이지에 삽입 | 유출 시 어느 계정에서 샜는지 추적 (§7.3) |

## 8. 고객 경험 원칙 (Apple 벤치마크)

"전세계적으로 독보적인 교육 포털"이 목표라면, 기능이 많은 것보다 **압도적으로 직관적인 것**이 더 큰 차별화 포인트입니다. Apple류 제품의 공통점을 벤치마킹해 원칙으로 못 박습니다.

### 8.1 화면당 하나의 결정
Apple, Stripe 등 전환율이 높은 서비스는 한 화면에서 사용자에게 결정을 하나씩만 요구합니다. 지금 프로토타입의 회원가입·체크아웃 화면은 필드가 여러 개 한 번에 나오는 구조인데, 실제 폼 구현 단계에서는 단계를 잘게 쪼개는 것을 원칙으로 삼습니다 (예: "누구신가요?" → "닉네임" → "보호자 연락처" → "동의" 를 한 화면이 아니라 순차 화면으로).

### 8.2 신뢰 지표는 숨기지 않고 보여준다
대부분의 경쟁 서비스는 콘텐츠 품질 검증 이력이나 완주율을 공개하지 않습니다. MakerStudio는 반대로 갑니다 — §6.3에서 도입한 `lastVerifiedAt`(마지막 검증일), 완주 학습자 수, 평점을 코스 상세 화면에 정직하게 노출합니다. 이는 지금까지 지켜온 "다크패턴 없음, 화폐를 숨기지 않는다"는 원칙과 결이 같고, 동시에 실질적인 차별화 요소가 됩니다.

### 8.3 업데이트는 투명하게, 기존 사용자는 보호하게
§6.3의 버전 관리 정책과 연결됩니다 — 코스가 업데이트되면 "이번 업데이트에서 달라진 점"을 App Store 업데이트 노트처럼 보여주고, 이미 학습 중이던 사용자의 진행 흐름은 갑자기 바뀌지 않도록 보호합니다.

### 8.4 피드백 → 개선까지 닫힌 고리(closed loop)로
각 모듈에 "이 모듈 개선 제안하기" 버튼을 두고, 제출되면 §5.5의 이벤트 체계를 통해 자동으로 §6.3의 `REVISION_DRAFT` 생성 파이프라인에 티켓으로 들어가게 합니다. 사람이 수동으로 챙기지 않아도 시스템이 스스로 개선 사이클을 도는 구조입니다.

### 8.5 코스 평점·리뷰 — §8.2·§6.7·§6.3을 잇는 실제 데이터 소스

§8.2에서 "완주율·평점을 정직하게 공개한다"고 정했지만 실제로 그 데이터가 어디서 나오는지 정의된 적이 없었습니다. 평점·리뷰 시스템으로 이를 채우고, 동시에 §6.7에서 "행동 데이터가 없어 못 쓴다"고 했던 공백도 채웁니다.

**작동 방식**
- 코스를 완료한 학습자에게만 평가 요청 노출 (완료 전에는 요청하지 않음 — 미완주자의 평가는 신뢰도가 낮음)
- 별점(1~5, 필수) + 서술형 코멘트(선택)로 구성
- 별점은 즉시 공개 반영, 서술형 코멘트는 **경량 자동 필터(욕설·개인정보 패턴 감지) 통과 후 공개** — 특히 미성년 학습자가 작성자일 수 있어, 관리자가 모든 리뷰를 수동 검수하는 방식(확장 불가)이 아니라 자동 필터 + 신고 시 검수하는 방식을 채택합니다.

**다른 섹션과의 연결**
| 대상 | 어떻게 쓰이는가 |
|---|---|
| §8.2 신뢰 지표 | 카탈로그·코스 상세에 "⭐ 4.6 (128명 평가)" 형태로 정직하게 노출 |
| §6.7 관련 코스 추천 | **평가 건수가 최소 표본(예: 20건) 이상인 코스에 한해** "많이 학습한/평점 높은" 같은 행동 기반 문구 사용 가능. 표본이 적을 때 "인기"라고 부르면 왜곡된 신호이므로, 최소 표본 규칙을 반드시 지킵니다. |
| §6.3 콘텐츠 생애주기 | 특정 모듈에 낮은 평점이 반복되면 §8.4의 개선 제안과 마찬가지로 `REVISION_DRAFT` 파이프라인에 자동으로 신호를 보낼 수 있습니다 (임계치는 운영하며 조정) |
| §5.5 도메인 경계 | 평가 제출은 `learning` 도메인이 처리하고, `learning.review_submitted` 이벤트를 발행 — `content` 도메인(신뢰지표·추천·개정신호)과 `moderation` 도메인(자동 필터 결과 신고 검수)이 각자 구독만 하면 됩니다. `learning` 도메인은 이 데이터가 어디에 쓰이는지 몰라도 됩니다. |

## 9. 품질 보증 원칙 (상설 — §7·§8과 같은 성격, 계속 재확인)

"설계서가 좋으면 오류 없이 개발된다"는 보장은 없습니다. 설계는 방향과 구조를 정하는 것이지 구현 단계의 실수까지 막아주지 않습니다. 대신 **오류가 나더라도 싸게, 빨리 발견해서 고칠 수 있는 상태**를 목표로 삼고, 이를 위한 습관을 지금부터 코드베이스에 박아둡니다.

### 9.1 자동 테스트 없이는 배포하지 않는다
- **콘텐츠 검증**: §6.3의 `validate-content`(스키마) + `validate-arduino`(실제 avr-gcc 컴파일)가 이미 이 원칙의 실제 구현체입니다.
- **단위 테스트**: 순수 로직(예: `lib/rate-limit.ts`의 사용량 제한 규칙)부터 시작합니다. Node.js 내장 테스트 러너(`node:test`)를 사용해 별도 패키지 의존성을 늘리지 않았습니다(§5.2의 "단종 위험 낮은 도구" 원칙과 일관). `npm test`로 실행하며, CI(`.github/workflows/ci.yml`)가 PR마다 자동으로 돌립니다.
- **통합/E2E 테스트**: 로그인, 결제, 퀴즈 채점처럼 여러 컴포넌트가 얽히는 핵심 사용자 흐름은 Phase 3 이후 Playwright 같은 도구로 확장합니다.
- **원칙**: 새 기능(특히 §5.5의 각 도메인 경계를 넘나드는 로직, 결제·인증 관련 로직)을 추가할 때는 최소 하나 이상의 자동 테스트를 함께 작성하는 것을 기본으로 합니다.

### 9.2 배포 후 모니터링 — 실사용에서 터지는 문제는 테스트로 못 잡는다
테스트를 아무리 잘 짜도 실제 사용자 환경(브라우저 종류, 네트워크 상태, 예상 못 한 입력값)에서만 드러나는 문제가 있습니다. Sentry 같은 에러 모니터링 도구 도입을 권장합니다 — Sentry는 오픈소스로 자체 호스팅도 가능해 §5.2의 "벤더 종속 회피" 기준에도 맞습니다.

### 9.3 단계적 배포 — 한 번에 다 열지 않는다
- **기능 플래그**: 리스크가 큰 신규 기능(결제 흐름 변경 등)은 일부 사용자에게만 먼저 노출한 뒤 전체 오픈합니다.
- **파일럿 우선**: §14.1에서 결정한 대로 개인 학습자(B2C)를 먼저 가더라도, **처음엔 소규모로 시작해 문제를 먼저 걸러내는 것**을 원칙으로 합니다.
- **롤백 용이성**: Vercel은 Git 커밋 단위로 배포되어 이전 배포로 즉시 롤백이 가능합니다(§5.2에서 이미 이 이유로 선택한 스택) — 별도 롤백 도구를 새로 만들 필요가 없습니다.

### 9.4 사용자 리포트 → 개선 흐름과 연결
§8.4의 "이 모듈 개선 제안하기"와 마찬가지로, 버그 신고도 §5.5의 이벤트 체계를 통해 자동으로 개발 백로그에 티켓으로 들어가게 합니다. 사람이 커뮤니티 게시판을 일일이 확인하지 않아도 됩니다.

**우선순위 이유**: 결제·로그인을 먼저 만들면 "팔 콘텐츠가 없는 상태에서 계산대만 있는" 상황이 됩니다. Duolingo도 Code.org도 콘텐츠와 무료 사용자 기반을 먼저 만든 뒤 수익화를 얹었습니다. 복합 키트 코스(Phase 7)는 개별 보드 모듈 라이브러리가 어느 정도 쌓인 뒤에 배치했는데, 코스는 기존 모듈을 재조합하는 작업이라 모듈이 적은 상태에서는 재조합할 재료 자체가 부족하기 때문입니다.

**Phase 4/5 순서 조정 이유 (§14.1 "초기 타겟" 결정 반영)**: 학교·학원 영업 채널이 전무하고 초기 자본도 빠른 매출이 필요한 상황이라, 콜드 세일즈가 필요한 B2B(교사 대시보드·학급 라이선스)를 먼저 만드는 건 판매할 곳 없는 제품을 먼저 만드는 낭비가 됩니다. **개인 구독 결제(셀프서브, 승인 라인 없음)가 훨씬 빠르게 매출로 이어지므로 Phase 3·5(개인 결제 부분)를 먼저 완성**하고, B2B는 개인 사용자 중 교사가 자연 유입되는 것을 계기로 나중에 투자합니다.

> 참고: UI 프로토타입(로그인/마이페이지/교사·보호자 대시보드/요금제/카탈로그/코스 목차/관리자 검수 — 총 11개 화면)은 Phase 3~7의 디자인 검토용으로 이미 완성되어 있습니다. 실제 데이터와 연결하는 작업은 각 Phase의 로그인/DB가 갖춰진 뒤 진행합니다 (실제 코드베이스와 UI 목업을 의도적으로 분리 운영 중 — 80% 이상 검증되면 통합 예정).

## 13. 사업화 준비도 점검 — 마케팅·SEO·운영 인프라

지금까지 설계한 것은 전부 **"가입한 다음"의 경험(앱)** 입니다. **"애초에 사람들이 이 사이트를 어떻게 알게 되는가"** 는 설계된 적이 없고, 이게 지금 시점에서 가장 큰 공백입니다. 제품이 아무리 좋아도 이 부분이 없으면 사업으로서 성립하지 않습니다.

### 13.1 구글 활용 — 애드센스는 배제, 애즈+SEO는 필수

| 구글 도구 | 채택 여부 | 이유 |
|---|---|---|
| **Google 애드센스** (사이트에 광고 노출) | ❌ 채택 안 함 | COPPA(아동 온라인 개인정보 보호법) 준수를 위해 아동 대상 서비스 태그를 붙이면 관심기반·리마케팅 광고가 꺼져 단가가 크게 떨어짐. 유료 구독 모델과 광고 모델을 섞으면 프리미엄 포지셔닝도 훼손됨 |
| **Google Ads** (검색광고로 유입) | ✅ 필요 | 초기 타겟이 개인(B2C) 우선으로 확정된 이상(§14.1), 유료 검색광고는 현실적인 초기 획득 채널. 단, 광고를 걸 랜딩페이지가 아직 없음(§13.2) |
| **Google 검색(SEO, 자연 유입)** | ✅ 필요, 현재 불가능한 상태 | 지금 설계된 화면이 전부 로그인 뒤에 있어 구글이 색인할 공개 페이지가 하나도 없음 |

### 13.2 SEO를 위해 반드시 필요한 것 — 공개 마케팅 사이트

**§7.2("잠긴 콘텐츠는 SSG 금지")는 로그인 뒤의 유료 콘텐츠에만 해당합니다.** 이것과 별개로, 다음 같은 **공개 페이지는 오히려 정적 생성(SSG)이 SEO에 유리**하므로 반드시 추가해야 합니다.

- **랜딩 페이지**: 지금까지 설계한 모든 화면(로그인/카탈로그/학습 등)은 "이미 가입한 사람"을 위한 것입니다. 처음 방문한 사람에게 "MakerStudio가 무엇인지, 왜 써야 하는지"를 보여주는 공개 첫 화면이 없습니다.
- **블로그/가이드 콘텐츠**: "초등학생 코딩교육 추천", "아두이노 처음 시작하기" 같은, 학부모가 실제로 검색하는 키워드를 겨냥한 공개 글. Google Ads를 걸 목적지도, 자연 검색 유입의 진입점도 이 콘텐츠입니다.
- **구조화 데이터(Schema.org)**: 코스 목록에 `Course` 스키마, 키트에 `Product` 스키마를 붙이면 검색결과에 평점·가격이 바로 노출됩니다 — §8.5의 평점 시스템과 직결됩니다.
- **Core Web Vitals**: Next.js를 이미 선택해뒀기 때문에(§5.2) 기술적으로는 유리한 상태입니다.
- **E-E-A-T 연결**: §8.2("신뢰 지표는 숨기지 않고 공개")가 구글의 신뢰성 평가 기준과 이미 잘 맞습니다. 콘텐츠에 전문가 저자 정보, 검증일 등을 노출하면 SEO에도 도움이 됩니다.

### 13.3 그 외 사업화 공백 (마케팅과 별개로 점검 필요)

| 영역 | 빠진 것 |
|---|---|
| 리텐션 고도화 | 스트릭·배지는 있지만 푸시 알림, 난이도 적응, 소셜 경쟁 요소 등 정교함은 부족 |
| 운영 인프라 | 고객센터/FAQ/문의 채널 없음, 이용약관·개인정보처리방침 실제 문서 없음(원칙만 정의됨) |
| 측정 인프라 | 퍼널 분석, 코호트 리텐션 분석, A/B테스트 도입 설계 없음 |
| 유닛 이코노믹스 | 가격은 정했지만 LTV/CAC 계산, AI API 비용·호스팅비 등 실제 원가 구조 검증 없음 |
| 성장 루프 | 추천인 프로그램, 신학기·방학 시즌 프로모션 같은 자연 확산 장치 없음 |

### 13.4 로드맵 반영 제안

랜딩페이지·공개 콘텐츠는 로그인/DB가 필요 없는 순수 정적 페이지라, **Phase 3(로그인)를 기다릴 필요 없이 지금 로드맵과 병행해서 가장 먼저 시작할 수 있습니다.** 초기 타겟이 개인(B2C)이고 빠른 매출이 필요한 상황(§14.1)이라면, SEO는 결과가 나오기까지 시간이 걸리는 채널이라 **오히려 지금 당장 시작해야 Phase 5(결제) 완성 시점에 유입이 준비돼 있습니다.**

3. **부품 커머스 연동 방식**: 완전 통합 대신 API/딥링크 느슨한 연동 — §4-A/§4-B
4. **콘텐츠 소싱 전략**: 공식 예제 기반 모듈화 → 코스 재조합 — §6.5
5. **미성년자 결제**: 학생 화면에는 결제 버튼 없음, 보호자 대시보드가 유일한 결제 진입점 — §10
6. **콘텐츠 생애주기/버전 관리**: DRAFT→PENDING_REVIEW→PUBLISHED/WITHDRAWN, 반려-재작업 vs 반려-철회 구분 — §6.3
7. **아키텍처**: Next.js+Supabase+PostgreSQL 스택, 도메인별 느슨한 결합 구조 — §5.5
8. **회로 시뮬레이터**: Wokwi 임베드를 기본값으로 확정(§5.2) — 자체 컴파일 서버는 임의 코드 실행 보안 부담이 커서 채택하지 않음. 실제 구현 착수 시점에 Wokwi 임베드 조건(요금제·API 한도)만 최종 재검증
9. **초기 타겟: 개인 학습자(B2C) 우선** — 학교·학원 영업 채널이 전무하고 초기 자본도 빠른 매출이 필요한 상황이라, 콜드 세일즈가 필요한 B2B보다 셀프서브 개인 구독이 매출까지의 시간이 훨씬 짧음. 로드맵 Phase 3·5(개인 결제)를 Phase 4(교사 대시보드/B2B)보다 먼저 진행하도록 조정(§11) — 2026-08-13 결정
